## 2026-10-02 · 固件编译 cc1plus out of memory [已解决]

- **现象**:`idf.py build` 在 nvs_flash 一批 C++ 文件上批量失败,`cc1plus.exe: out of memory allocating 65536 bytes`。
- **根因**:ninja 默认按 CPU 核数并行,每路 xtensa g++ 峰值 ~1GB;机器上同时跑着后端服务、隧道等,内存被挤爆。
- **解决**:构建目录已 configure 完成,直接 `ninja -C build -j 2` 限流续编。
- **教训**:这台机器上 IDF 全量编译要限并行(-j 2~3);"一批文件同时失败+out of memory"先查内存并行度,不是代码错。

## 2026-10-02 · ZCode 沙箱:env -u 派生的子进程 stdout 静默丢失 + idf.py MSYSTEM 分支跳过 main [已解决]

- **现象**:①`env -u MSYSTEM <任意 exe>`(cmd.exe/python)都 rc=0 但**零输出**,重定向到文件也是 0 字节;②不带 env -u 直接跑 idf.py,打印一句 "MSys/Mingw is no longer supported" 后静默退出——idf.py 的 `__main__` 里 MSYSTEM 分支**只 print_warning 不调用 main()**。
- **根因**:ZCode 沙箱对经 `env` 工具派生的子进程接管了 stdout 管道(与前棒 WorkBuddy 的 PATH 重写是不同机制的同款体验);idf.py 对 MSYSTEM 的处理是"警告后继续但不执行 main"。
- **解决**:python 包装器 `D:\easy-input\tools\_idf_build.py`——在**本进程内** `os.environ.pop("MSYSTEM")`(子进程继承干净 env,不走 env 工具)、`sys.path.insert` 补 IDF tools 目录与 venv site-packages(启动后改 PYTHONPATH 无效)、再 `runpy.run_path(idf.py, run_name="__main__")`。idf.py 全速执行,cmake/ninja/编译器经 CMAKE_PROGRAM_PATH+PATH 环境变量下发,构建成功。
- **教训**:沙箱里"改子进程 env"要么在父 python 进程内改(能穿透),要么显式传参;任何"无输出但 rc=0"先怀疑包装层吞输出,用 `python -c print` 做最小验证。

## 2026-10-02 · 云端链路四连坑(TTS/ASR/回调测试)[已解决]

- ①**cosyvoice-v2 音色名必须带 `_v2` 后缀**(longxiaochun→longxiaochun_v2),否则 InvalidParameter 418,报错不提示原因;
- ②**dashscope SDK 1.27 的回调类是 `RecognitionCallback`**,老教程的 `Recognition.Callback` 属性不存在;
- ③**TTS 流式输出的 WAV 头 size 字段是占位垃圾值**(声明 67108 秒):SDK 为流式设计,`call()` 拿到的头未回填——落盘前修正 RIFF/data size,ASR 侧干脆解析裸 PCM 以 format='pcm' 直送,双保险;
- ④**curl -F 传中文在 Windows 按 GBK 编码发送**:导致 TTS"念乱码"、ASR"转写乱码"的假故障(同一乱码文本→确定性输出,两次结果一字不差是关键线索);测试统一走 Python httpx,且 **localhost 访问要 `trust_env=False`**(httpx 默认走系统代理,127.0.0.1 被代理截胡)。
- **教训**:云端集成测试全部用代码客户端,不信任终端工具的编码;一次"结果完全复现的错误"优先怀疑上游输入而不是下游随机性。

## 2026-09-28 · idf.py 的 cmake 死活找不到 xtensa 编译器(沙箱 PATH 重写)[已解决]

- **现象**:PowerShell 里给 idf.py 设好完整 PATH(xtensa-esp-elf\bin 在最前),idf.py 能跑、cmake 能起,但 cmake 报 `CMAKE_CXX_COMPILER (xtensa-esp32s3-elf-g++) is not a full path and was not found in the PATH`。探针验证:PowerShell 进程内 Get-Command 能解析编译器,**但任何子进程(python/cmake)看到的 PATH 都被换成 safe-bin shim 打头的另一套**。
- **试过没用的**:①profile 别名法激活(`. Microsoft.v5.5.5.PowerShell_profile.ps1`)——脚本只设变量不挂 PATH;②Git Bash 跑 idf.py——MSYSTEM 会被沙箱重新注入,idf.py/idf_tools.py 直接拒跑;③`-D` 传给主工程——bootloader 是嵌套 cmake,收不到。
- **根因**:WorkBuddy 工具沙箱在创建子进程时重写 PATH,**会话内对 `$env:PATH` 的修改传不到子进程**;idf.py → cmake → 编译器查找链上工具链目录消失。
- **解决**:不依赖 PATH。①主工程 `idf.py -B build -D "CMAKE_PROGRAM_PATH=<工具链bin>"`;②bootloader 用 `CMAKE_PROGRAM_PATH` **环境变量**(cmake 从同名 env 初始化缓存,普通 env 能穿透沙箱);③`IDF_CCACHE_ENABLE=0`;④**构建必须从 PowerShell 通道走**。完整命令固化在 `D:\easy-input\easy-input-maker-rims\rims-mvp\README.md`。
- **教训**:这台机器上「设 PATH 再跑子进程」在 WorkBuddy 会话内不可靠;凡 find_program 类解析一律用显式路径参数(host_test 的 CMAKE_C_COMPILER 显式路径、IDF 的 CMAKE_PROGRAM_PATH,同一招)。

## 2026-09-28 · host 测试抓到 ASKING 死锁(设计漏洞)[已解决]

- **现象**:节流用例没发 RECORD_STARTED,状态机卡死在 ASKING,后续所有开门事件被吞。
- **根因**:ASKING → IDLE 只认 RECORD_STARTED→RECORD_DONE 路径;录音启动失败时无出口。
- **解决**:RECORD_DONE 在 ASKING 态也接受(兜底回 IDLE),补用例 `test_ask_recovers_when_record_never_starts`(firmware/components/door_event_policy + rims-mvp 同步)。
- **教训**:「纯逻辑先上 host 测试」的兑现——这个坑若到实板才发现,排查要横跨固件+云端。

## 2026-09-28 · C 组件被 C++ 测试链接报 undefined reference[已解决]

- **现象**:`door_event_policy_tests.cpp` 链接报 `undefined reference to depo_step(...)`,但编译都过了。
- **根因**:C 头文件没包 `extern "C"`,C++ 按名字修饰找符号,C 编译的目标文件里没有。
- **解决**:所有给 host_test 用的 C 头文件一律加 `#ifdef __cplusplus extern "C" {` 包裹(door_event_policy.h、board_pins.h 均已加)。
- **教训**:纯逻辑组件的头文件模板里 extern "C" 是标配,不是可选项。

## 2026-09-28 · CMake 配置报 CMAKE_CXX_COMPILER not set[已解决]

- **现象**:Git Bash 里 `cmake -S host_test -B build-host` 直接报 `CMAKE_CXX_COMPILER not set` / nmake 找不到。
- **根因**:PATH 里没有任何 C/C++ 编译器;本机可用工具链是 `D:/easy-input/tools/winlibs/mingw64/bin`(gcc/g++/ninja)。
- **解决**:配置时显式指定 `-G Ninja -DCMAKE_MAKE_PROGRAM=.../ninja.exe -DCMAKE_C_COMPILER=.../gcc.exe -DCMAKE_CXX_COMPILER=.../g++.exe`(已写进 firmware/AGENTS.md 验证命令)。
- **教训**:新项目 host_test 直接照抄 easy-input-maker 的配置参数,不要裸跑 cmake。

## 2026-10-03 · S3 USB-Serial-JTAG 复位必进下载模式（应用烧完不启动的根因）[已解决]

- **现象**:rims-mvp 烧录成功(hash 全过)后热点不出现;esptool `--after hard_reset`、手动 RTS 脉冲(DTR 恒 False)一律落回 `rst:0x15 (USB_UART_CHIP_RESET), boot:0x0 (DOWNLOAD(USB/UART0))  waiting for download`。
- **根因**:ESP32-S3 ROM 的默认行为——凡从 USB-Serial-JTAG 口触发的复位(USB_UART_CHIP_RESET),只要没烧 `DIS_USB_DOWNLOAD_MODE` eFuse,一律进下载模式。**烧录后的 hard reset 也算**,所以"烧完不启动"不是固件问题,是复位路径问题。T12 当年"烧完必须断电重开"是同一件事。
- **解决**:烧录后**电源开关完全断电再开机**(RTC 上电复位,走正常启动)。开发期可挂被动串口监听抓真实启动日志;注意任何主动 DTR/RTS 序列都会打回下载态,污染观测(本次 12 秒空抓的教训)。
- **量产方案**:烧 `DIS_USB_DOWNLOAD_MODE` eFuse(牺牲 USB 下载口,配合 OTA);或在应用启动后用 `boot_mode` 检测提示用户断电重启。
- **教训**:S3 USJ 板的"烧录成功"和"应用运行"之间,永远隔着一次真断电重启;验证应用启动要用 Wi-Fi/外设证据,不能用"esptool 连得上连不上"。
